## 핵심 구현 및 학습 내용

### 1. Multi-Thread & Concurrency (멀티스레드 및 동기화)

#### ① ThreadManager
* **도입 목적**: 서버에 필요한 다수의 작업 스레드를 일관되게 생성, 관리하고 서버 종료 시 안전하게 조인(Join)하도록 돕는다.
* **구현 방식**: 스레드 생성 시 스레드 로컬 영역(TLS)에 고유한 스레드 ID(`LThreadId`)를 부여하여 로그 기록 및 로컬 자원 접근 시 경합을 최소화한다. 또한 스레드 엔트리 함수를 래핑하여 예외 처리 및 초기화 작업을 단일 지점에서 제어한다.

#### ② DeadLockProfiler
* **도입 목적**: 멀티스레드 환경에서 락을 획득하는 순서가 꼬여 발생하는 데드락(Deadlock) 버그를 예방하고 추적하기 위해 도입하였다.
* **구현 방식**: 
  * 스레드가 락을 획득할 때마다 **어떤 락을 잡은 상태에서 다른 락을 요청했는지**를 기록하여 락 획득 관계를 방향성 그래프(Directed Graph)의 간선(Edge)으로 등록한다.
  * 새로운 간선이 등록될 때마다 깊이 우선 탐색(DFS) 알고리즘을 사용해 **그래프에 사이클(Cycle)이 존재하는지** 실시간으로 검증한다.
  * 만약 사이클이 발견되면 이는 데드락이 발생할 가능성이 있는 위험 상황이므로, 즉시 크래시(`CRASH`)를 발생시켜 호출 스택(Call Stack)을 남김으로써 문제를 즉각적으로 찾아내어 해결할 수 있도록 돕는다.

#### ③ Lock (Custom Read-Write Lock)
* **도입 목적**: 데이터 읽기 빈도가 높고 쓰기 빈도가 낮은 공유 자원을 보호할 때, 표준 `std::mutex`보다 경합 비용을 대폭 줄이기 위해 구현하였다.
* **구현 방식**:
  * **SpinLock 계열의 RW Lock**: 32비트 정수 플래그 하나를 이용해 상위 16비트는 쓰기 스레드 상태(Write Flag), 하위 16비트는 읽기 스레드 개수(Read Count)로 매핑하여 비트 연산과 `compare_exchange_weak`(CAS)을 통해 동기화를 수행한다.
  * **재귀적(Recursive) 락 지원**: 동일한 스레드가 이미 쓰기 락을 소유한 상태에서 다시 쓰기 혹은 읽기 락을 획득하는 재귀적 진입을 허용하여 코드가 스레드 자신에 의해 블로킹되는 문제를 예방한다.

#### ④ TLS (Thread Local Storage)
* **도입 목적**: 전역 변수에 접근할 때 발생하는 스레드 간의 캐시 일관성 경합(Contention)을 최소화하기 위해 개별 스레드 고유의 저장 공간을 활용한다.
* **구현 방식**: `thread_local` 키워드를 사용하여 각 스레드별 고유 ID(`LThreadId`), 로컬 메모리 풀의 캐시 객체, 스레드 전용 일시적 메모리 버퍼 등을 할당함으로써 락(Lock) 없이 고속으로 데이터에 접근할 수 있도록 돕는다.

### 2. Memory Management (메모리 관리 및 최적화)

#### ① Custom Allocators
* **StompAllocator (메모리 오염 방지 할당자)**:
  * **목적**: 디버깅 시점에 메모리 침범(Overrun/Underrun) 및 해제된 메모리를 다시 참조하는 Use-After-Free 버그를 즉각적으로 잡아내기 위해 도입하였다.
  * **원리**: Windows의 가상 메모리 관리 함수인 `VirtualAlloc`을 사용하여 객체 크기에 맞춰 메모리 페이지를 할당하되, 할당된 페이지 바로 뒤에 접근 불가능한 **페이지 보호막(PAGE_NOACCESS Page)**을 강제로 배치한다. 만약 객체의 경계를 단 1바이트라도 넘어서 쓰는 오버런이 발생하면 그 즉시 하드웨어 예외(Access Violation)가 터져 버그가 발생한 정확한 소스 코드 라인을 검출한다. 또한 메모리를 해제할 때도 즉시 페이지 권한을 `PAGE_NOACCESS`로 변경하여 해제된 메모리 접근 시 즉각적인 크래시를 유도한다.
* **PoolAllocator (풀 기반 할당자)**:
  * **목적**: 기본 `malloc`/`free`가 유발하는 시스템 콜 비용과 메모리 파편화를 예방한다.
  * **원리**: 빈번하게 해제되고 생성되는 특정 크기의 자원들을 미리 할당해 둔 메모리 풀에서 꺼내어 재사용하도록 돕는다.

#### ② MemoryPool & ObjectPool
* **MemoryPool**:
  * 크기별로 메모리 블록을 세분화하여 관리하는 고정 크기 메모리 풀(Fixed-Size Block Pool)을 구현하였다.
  * 멀티스레드 경합을 최소화하기 위해 스레드 로컬(TLS) 메모리 풀 캐시를 우선적으로 거치도록 설계하여 락 프리하게 메모리를 할당할 수 있도록 최적화하였다.
* **ObjectPool**:
  * 단순히 바이트 단위의 메모리만 빌려오는 것이 아니라, 객체의 생성자 및 소멸자 호출 과정을 안전하게 자동화하는 풀링 래퍼 클래스를 제작하여 타입 안전성을 높였다.

#### ③ RefCounting (참조 횟수 관리 스마트 포인터)
* **도입 목적**: 멀티스레드 서버 환경에서 여러 세션이나 작업 스레드가 동일한 자원을 공유할 때, 해당 자원이 해제되어 댕글링 포인터(Dangling Pointer)가 되는 현상을 막고 안전하게 자동 소멸을 지원하기 위해 설계하였다.
* **구현 방식**: 
  * `RefCountable` 기본 클래스를 정의하여 객체 내부에 원자적 카운트(`atomic<int32>`) 변수를 배치(Intrusive 방식)한다.
  * 이를 제어하기 위해 `shared_ptr`과 유사한 커스텀 스마트 포인터 클래스 템플릿(`SharedPtr`)을 만들어 객체 참조 시 카운트를 원자적으로 증가시키고, 소멸자 호출 시 감소시켜 0이 되는 순간 자원을 안전하게 파괴하도록 구현하였다.

#### ④ STL Containers with Custom Allocator
* **도입 목적**: STL 컨테이너(`std::vector`, `std::list`, `std::map` 등)의 기본 메모리 할당 방식(`std::allocator`)은 동적으로 크기가 확장될 때마다 범용 힙 할당을 수행하여 파편화를 유발한다.
* **구현 방식**: 템플릿 할당자 인터페이스를 커스텀 구현하여 우리가 설계한 고속 `MemoryManager`와 연동시켰다. 이를 통해 컨테이너가 요소를 추가/삭제할 때 자체 메모리 풀을 사용하여 메모리 성능을 대폭 향상하고 단편화를 원천 예방한다.

### 3. Network I/O Models (네트워크 입출력 모델)

#### ① Select 모델
* **개념**: 단일 스레드로 감시하고자 하는 소켓 목록인 `fd_set`을 구성한 후, `select` 함수를 호출하여 준비 상태가 된 소켓이 생길 때까지 대기하는 I/O 멀티플렉싱 모델이다.
* **치명적인 단점 (파괴적 필터링)**:
  * `select` 함수가 반환될 때 이벤트가 발생하지 않은 소켓들을 `fd_set`에서 전부 소멸시켜 버리는 **파괴적인 성향**을 띤다.
  * 이 때문에 매 루프 시작 시점마다 관찰 대상을 새로 `FD_ZERO` 하고 `FD_SET`으로 모든 소켓을 재등록해야 하므로, 등록된 소켓 수($N$)에 비례하여 유저-커널 공간 사이의 메모리 복사와 반복 연산 비용이 유발되는 명확한 한계를 지닌다.

#### ② WSAEventSelect 모델
* **개념**: 소켓과 Windows OS가 관리하는 커널 이벤트 객체(`WSAEVENT`)를 1:1로 매핑하여 네트워크 이벤트를 비동기적으로 감지하는 모델이다.
* **동작 방식**: 
  * `WSAEventSelect` 함수를 호출하여 소켓에 관심 있는 이벤트 종류(`FD_READ`, `FD_WRITE`, `FD_CLOSE` 등)를 이벤트 객체와 연동한다.
  * `WSAWaitForMultipleEvents` 대기 함수를 사용하여 여러 이벤트 핸들을 동시에 감시하며, 이벤트 발생 시 `WSAEnumNetworkEvents`를 통해 구체적으로 어떤 이벤트가 발생했는지 확인 후 알맞은 I/O를 수행한다.
* **특이사항 및 제약**:
  * 소켓과 이벤트 객체의 연결 정보가 커널 내에 유지되므로 Select 모델처럼 매 루프마다 관찰 리스트를 재등록할 필요가 없다.
  * `WSAEventSelect` 호출 성공 시 해당 소켓은 **자동으로 넌블로킹 모드**로 변환된다.
  * 하나의 대기 함수에서 동시에 감시할 수 있는 이벤트 핸들의 개수가 최대 **64개**(`WSA_MAXIMUM_WAIT_EVENTS`)로 물리적인 제한이 걸려 있다.

#### ③ Select vs WSAEventSelect 비교
| 구분 | Select 모델 | WSAEventSelect 모델 |
| :--- | :--- | :--- |
| **감지 메커니즘** | 소켓 셋(`fd_set`) 비트 배열 검사 | Windows 이벤트 객체(`WSAEVENT`) 감지 |
| **목록 보존성** | **파괴적 (Destructive)** (매 루프 재조립 필요) | **비파괴적 (Persistent)** (커널이 매핑 유지) |
| **메모리 복사** | 매 루프마다 전체 목록을 유저-커널 간 복사 ($O(N)$) | 최초 등록 시에만 전달하므로 복사 비용 거의 없음 |
| **동시 대기 제한** | 윈도우 기본 64개 (임의 확장 가능하나 비권장) | 스레드당 최대 64개 (`WSA_MAXIMUM_WAIT_EVENTS`) |
| **이식성** | **OS 독립적** (POSIX 표준) | **Windows 종속적** (Winsock API) |

### 4. Utilities & Helpers

#### ① TypeCast (Fast Type Cast)
* **도입 목적**: C++ 표준 RTTI 기반의 `dynamic_cast`는 상속 관계의 클래스 계통도를 런타임에 직접 순회하며 안전성을 검사하기 때문에 속도가 매우 느려 서버 프레임워크의 고속 루프에 적합하지 않다.
* **구현 방식**:
  * 다형성 클래스군에 고유한 타입 ID 상수를 정적으로 정의해 둔다.
  * 컴파일 타임 템플릿 메타 프로그래밍과 커스텀 `TypeCast` 도우미를 구현하여, 캐스팅 시 타입 ID 비교만으로 형변환의 타당성을 판단하도록 설계하였다.
  * 이를 통해 런타임 탐색 연산 비용을 $O(1)$의 상수 시간으로 줄이면서도 잘못된 형변환 시 `nullptr`를 반환하거나 빌드 타임에 에러를 유발해 안정성을 보장한다.
